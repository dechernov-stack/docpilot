# DocPilot · тестовый P0

Рабочий прототип механики инженерного документа по ТЗ: ConOps насосной станции хранится как структура в SQLite, экспортируется в StrictDoc, базируется в отдельном Git-репозитории, превращается детерминированным STUB-рендерером в читаемый текст, проходит защищённую рецензию и выпускается в печатные форматы.

## Быстрый запуск

Требуется Docker Desktop / Docker Compose.

```bash
docker compose up --build
```

После готовности контейнеров открыть <http://localhost:8080>. OpenAPI доступен через <http://localhost:8080/api/docs>.

Порт публикуется только на loopback. Если `8080` занят, задайте другой: `DOCPILOT_PORT=18081 docker compose up --build`.

Данные и внутренний Git-репозиторий сохраняются в volume `docpilot-data`. Чтобы начать демонстрацию с чистого seed, остановите Compose и удалите этот volume командой `docker compose down -v`.

## Тур на 10 минут

1. Откройте «Документ» на ступени `SRR`: документ показывает `3/4`, а §3 — `2/3 сценария`, с явным действием «добавить».
2. Переключитесь на `MCR`: все четыре раздела полны.
3. Вернитесь в `SRR`, нажмите строку нехватки в §3, создайте сущность «Восстановление после аварии» и сохраните её как элемент. Полнота станет зелёной.
4. На экране «Элемент» выберите «Тезис» и попробуйте сохранить текст `Давление 7 бар` без опоры. API вернёт структурированную ошибку `400 ELEMENT_INVALID`.
5. Откройте «Базирования», оставаясь в роли `si`, и создайте `MCR`: появится неизменяемый тег `BL-MCR-1`, Git hash и автор.
6. Добавьте или измените структуру, создайте второй `MCR`, выберите два тега и нажмите «Сравнить». Диф строится по стабильному MID и показывает поля узла.
7. В «Рендеринге» выберите baseline и нажмите «Сгенерировать». Индикатор честно показывает `STUB`; каждое утверждение заканчивается `[MID]`.
8. Наведите на `[MID]`: справа появится исходный элемент. Переключитесь на роль `rev`, откройте рецензию и переставьте слова — патч сохранится.
9. Попробуйте заменить `120 м³/ч` на `90 м³/ч`: сервер вернёт `422 REVIEW_SEMANTICS_CHANGED`, текст останется прежним. Примите допустимый рендеринг.
10. В «Печати» выпустите пакет. Авторы вычисляются из элементов baseline, рецензента и выпустившего; доступны два PDF и, по желанию, DOCX.

## Что действительно реализовано

- SQLite-схема сущностей ТЗ и детерминированный seed: 8 фактов, 11 сущностей, 12 элементов, 4 раздела.
- Полнота по ожиданиям шаблона отдельно для MCR/SRR.
- Формы шести видов элементов; ссылки выбираются из базы, число в тезисе требует опору.
- Детерминированная генерация `docs/ConOps.sdoc`; SHA-сторож защищает и структурный, и изложенный `.sdoc` от молчаливого перезаписывания ручных правок.
- StrictDoc 0.29.0 реально разбирает оба `.sdoc`. В этой версии команды `strictdoc check` нет, поэтому эквивалентная проверка выполняется через parse+JSON export; режим возвращается как `strictdoc-export-parse`.
- Baseline = запись SQLite + Git commit + аннотированный тег. GitPython используется как основной адаптер, CLI — только fallback.
- Собственный field-level diff по MID: added / changed / removed, без шума от технического поля `version`.
- STUB-рендеринг только из snapshot элементов выбранного baseline; отпечаток входа, отдельный commit `rendered/ConOps.sdoc` и текстовый диф с предыдущим рендерингом документа.
- Guard чисел: даты ISO и номера разделов исключаются, остальные числа должны существовать в данных указанного `[MID]`.
- Рецензия хранит diff-match-patch; замена чисел, смысловых квалификаторов (`не`, `не менее`, `только` и т. п.) и удаление/добавление ссылок отклоняются атомарно.
- Вычисление авторов выпуска, HTML, два PDF-маршрута и DOCX P1.
- Единый формат ошибок `{code, message, reasons[]}`; роли и состояния не кодируются одним цветом.

## Печать и режимы выполнения

Docker-образ включает Typst 0.15.1, Chromium/Chromedriver и StrictDoc 0.29.0. В контейнере включён строгий нативный режим: выпуск считается успешным только при фактическом выполнении Typst и StrictDoc HTML2PDF; сбой возвращается структурированной ошибкой и не маскируется запасным PDF.

При локальной разработке без `DOCPILOT_NATIVE_PRINT=1` остаётся явный fallback на автономно сформированный PDF. StrictDoc установлен в проектную `.venv` и проверен настоящим парсером.

ИИ-провайдер в этом тестовом прогоне не используется: без ключа включён обязательный детерминированный STUB. Подключение внешнего LLM оставлено за границей безопасного demo slice; ключи не нужны и не сохраняются.

## Локальная разработка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
.venv/bin/uvicorn backend.app.main:app --reload
```

Во втором терминале:

```bash
cd frontend
npm install
npm run dev
```

Vite откроется на <http://localhost:5173> и проксирует `/api` на порт 8000.

Проверки:

```bash
.venv/bin/pytest
cd frontend && npm run build
cd ../e2e && npm install && npm test
```

Набор pytest покрывает AC-01…AC-11 и дополнительные негативные сценарии на временной SQLite и отдельном временном Git-репозитории. Playwright проводит один сквозной пользовательский сценарий с изолированной базой.

## Ответы на вопросы ТЗ

1. **Грамматика StrictDoc.** Типы узлов выражаются естественно через custom grammar. Условные правила (`число → supports`) остаются в доменном валидаторе. Для совместимости всем узлам добавлено одно контентное поле `STATEMENT`; произвольные списки хранятся как строки.
2. **Diff.** Для интерфейса выбран свой diff по MID: он стабильно даёт предметные поля и автора без зависимости от HTML-представления. Штатный `--generate-diff-git` оставлен как возможный печатный отчёт, но не как API-контракт.
3. **Guard чисел.** Практичен при разборе построчно с `[MID]`. Основные ложные срабатывания — даты, номера разделов и числа в идентификаторах; они исключены до проверки. Единицы сохраняются в сообщении об ошибке, сравнение выполняется по нормализованному числу.
4. **Typst против HTML2PDF.** Typst-шаблон компактнее и предсказуемее для титула/подписей; HTML2PDF лучше сохраняет представление StrictDoc. Для пакета точки полезно сохранять оба результата и показывать фактический движок каждого файла.
5. **UI поверх формата.** Главная собственная логика нужна для пикеров, полноты, роли, source-hover, защищённой рецензии и истории выпусков — эти сценарии не следуют напрямую из `.sdoc`. Формат отвечает за переносимую структуру, UI — за инженерный workflow.

## Известные границы тестового примера

- Один seed-проект и один документ; пароль и многопользовательская конкуренция намеренно отсутствуют.
- Реальный LLM adapter и ReqIF — следующие итерации.
- Нативный HTML2PDF зависит от Chromium; поэтому режим движка всегда возвращается вместе с файлом.
- Печатный Typst-шаблон демонстрирует титул, авторов, подписи и текст, но пока не содержит сложной отраслевой вёрстки таблиц/рисунков.
